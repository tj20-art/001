# 下单和登录性能测试副本

两份JMX由用户的“安全电商系统性能测试.jmx”复制整理，接口为当前项目的 https://127.0.0.1:2333，使用本地 users-local.csv 中的9个普通用户证书和密码。JMX本身没有硬编码密码。

## 使用前

1. 后端重启后必须显示“性能测试模式：开启”，登录限额10000次/300秒、普通接口限额6000次/60秒。PyCharm变量名为PERF_TEST_MODE，值1，名称末尾不能有空格。
2. 通过 performance/jmeter/start-jmeter-java21.bat 启动JMeter，避免Java24与Groovy不兼容。
3. CSV使用 C:/Users/r7000/PycharmProjects/PythonProject1/performance/data/users-local.csv，UTF-8、无表头，列名cert_path,password,product_id；不循环复用账号，最多9线程。
4. 商品ID来自CSV第三列，当前均为3；数量来自测试计划变量quantity，默认1。

## 默认打开即可联调

两份文件默认9线程、9秒升压、外层循环1次、业务循环1次。390秒是最长运行上限，默认业务一轮完成后会提前结束，并不等待390秒。

可先把线程组Number of Threads中的 `${__P(users,9)}` 改成1进行首轮验证；外层Loop Count始终保持1。测试计划里业务Loop Controller的 `${__P(loops,1)}` 默认一轮，可改为3或10。持续模式使用命令行参数，不改变外层循环。

### 下单性能测试

```text
线程组
├─ HTTP默认配置、CSV
├─ 初始化Once Only Controller
│  ├─ 证书+密码登录（检查普通用户角色及Token）
│  ├─ 获取公钥
│  └─ 检查购物车为空
└─ 业务Loop Controller
   ├─ 加入购物车（SM2+SM4-GCM加密及响应解密）
   └─ 创建订单（加解密、code=0、订单ID、201及商品数量金额断言）
```

每个账号的测试购物车必须为空。脚本不会自动删除已有购物车商品；若不为空，准备断言失败并停止对应线程。先在网页使用对应账号整理购物车。

实际下单会创建订单并扣库存，不包含支付。默认9用户一轮：9次登录+9次公钥+9次购物车检查+9次加购物车+9次创建订单，共45个HTTP样本。其中被测下单指标只看“03_创建订单”行，其他准备请求分别保留。

同一账号不要分配给多个并发下单线程。默认每账号一单一件、商品3，总消耗9件（初始购物车为空且全部成功时）。持续运行前需要专用测试数据、足够库存以及可重复的数据恢复步骤。

### 登录性能测试

```text
线程组（外层1次，CSV每线程固定账号）
└─ 业务Loop Controller
   └─ 证书+密码登录（code=0、Token及普通用户角色检查）
```

登录在每个业务循环中执行，不放Once Only Controller。默认9用户一轮共9次登录。修改业务循环10次即90次登录。测量范围是普通用户密码+证书登录，不包括管理员TOTP。

## 命令行入口和结果保存

PowerShell进入项目根目录：

```powershell
Set-Location 'C:\Users\r7000\PycharmProjects\PythonProject1'
```

先运行短时联调（选一个场景，分别运行）：

```powershell
& .\performance\run-performance.ps1 -Scenario login -Mode smoke -Users 9
& .\performance\run-performance.ps1 -Scenario order -Mode smoke -Users 9
```

确认成功并准备数据后才执行持续负载：

```powershell
& .\performance\run-performance.ps1 -Scenario login -Mode load -Users 9
& .\performance\run-performance.ps1 -Scenario order -Mode load -Users 9
```

模式load使用外层1次、内部无限循环、10秒升压、390秒上限；前70秒准备和预热，随后300秒为正式测量窗口。初始化须在该窗口前完成。登录间隔1000毫秒；加购物车和下单各500毫秒。优化前后保持同样配置。

运行入口会在 performance/results 下创建独立时间目录，保存原始raw.jtl、jmeter.log、实际使用的JMX和参数、全程HTML；持续模式还生成measurement.jtl、measurement.summary.json和正式窗口HTML。汇总p95统一采用summary的nearest-rank口径，保留失败样本。

若PowerShell执行策略阻止脚本，可仅对此次运行使用：`powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\performance\run-performance.ps1 -Scenario login -Mode smoke -Users 9`。下单时将Scenario改为order。不需要修改全局执行策略。

默认JMX保留结果树和聚合报告供界面联调；命令行入口生成禁用可视化监听器的副本，通过-l保存原始结果。直接从GUI运行不会自动生成这些独立结果目录。

## 已验证和仍需验证的部分

已通过原生JMeter 5.6.3+Java21在独立内存HTTP服务中的端到端验证：3个不同证书账号、2轮业务；下单21个HTTP样本全部成功、登录6个HTTP样本全部成功；请求和响应使用当前Python后端的加解密协议函数。已修复JMeter重复采样时原加密脚本正文模板恢复的问题。

这不是对真实数据库的性能测试，没有创建真实项目订单。真实账号状态、证书信任/吊销、商品库存和数据库并发行为仍需在项目环境验证。任何线程提前退出时，应检查错误和实际活动线程数，不能把低负载结果当作目标并发的有效基线。

第8、9周还需监控指标、三轮基线、瓶颈分析、优化提交、同条件复测与前后对比。生成JMX不代表验收已经完成。
